# Lima-shaped YAML project configuration: research and implementation plan

Status: design confirmed and implementation requested. Implemented in
`lima-debian-ctl/`; native forwarding has not been smoke-tested on a real VM.
No real-VM mutation has been authorized. This document supersedes its earlier
proposal variants.

## Accepted design

- Only the new YAML format is supported. No TOML compatibility or conversion
  command; remove the TOML parser dependency.
- Canonical filename: `.devvm.yaml`. `init` writes it and automatic discovery
  searches upward for that filename only. `--config PATH` can select another
  YAML filename explicitly.
- Every supported original Lima attribute is under `lima`, preserving original
  spelling, nesting and types. Controller-specific attributes are at the root;
  there is no `devvm` namespace.
- The controller continues to switch an existing provisioned VM. VM creation,
  images, driver, CPU/memory/disk sizing, networks and provisioning remain with
  `devbox-lima-template.yml` and Ansible.
- Minimum controller runtime dependency: Lima 2.3.0. Reject older versions
  before mutation. Test compatibility with newer versions rather than assuming
  they cannot change behavior.
- Keep the existing resolver/guest-file credential contract. Do not implement
  native `env`, invocation-only credentials or new environment backends.
- Preserve unrelated CLI behavior and existing JSON output conventions; adopting
  native YAML spelling does not require renaming every internal/output field.

## Supported attributes and correspondence

Publish this reference in the controller README and provide an editor JSON
Schema describing native correspondence, defaults, restrictions and backends.

| Project attribute | Original Lima attribute | Ownership / policy |
| --- | --- | --- |
| `lima.mounts[].location` | `mounts[].location` | Controller resolves and validates host paths; Lima mounts |
| `lima.mounts[].mountPoint` | `mounts[].mountPoint` | Explicit clean guest path beneath `/work/` |
| `lima.mounts[].writable` | `mounts[].writable` | Native default false |
| `lima.ssh.forwardAgent` | `ssh.forwardAgent` | Native default false; independent of custom forwarding |
| `lima.mountInotify` | `mountInotify` | Native default false; experimental feature |
| `lima.containerd.system`, `.user` | `containerd.system`, `.user` | Both forced false; true rejected because guest uses Docker |
| `lima.portForwards` | `portForwards` | Native forwarding only; never translated into our custom SSH rules |
| Root `schemaVersion`, `project`, `instance` | None | Controller identity and schema |
| Root `environment` | None | Existing host resolver and guest environment file |
| Root `portForwarding` | None | Explicit local-forwarding backend selector |
| Root `localTunnels`, `reverseTunnels` | None | Our SSH `-L` and `-R` rules |
| Generated catch-all ignore rule | Native `portForwards` rule | Controller-owned policy; prevents undeclared automatic forwarding |
| Resolver output | No mapping to Lima `env` | Secret-bearing; never written into Lima YAML/cidata/backups |

Whitelist only the native mount fields listed above, `ssh.forwardAgent`,
`mountInotify`, disabled-only `containerd`, and the native network-port rule
fields: `guestIP`, `guestIPMustBeZero`, `guestPort`, `guestPortRange`, `hostIP`,
`hostPort`, `hostPortRange`, `proto`, `static`. User-defined `ignore` rules are
not needed: policy is generated by the controller. Reject other keys, including
`guestSocket`, `hostSocket`, `reverse`, native `env`, `param`, mount-driver options
and unrelated nested SSH attributes.

Native network-port field/default validation follows Lima 2.3.0, with these
explicit controller restrictions: declared-only loopback exposure, unprivileged
controller-created listeners, no sockets, and verified backend capabilities.
The policy-generated ignore rule is not a user-configurable exception.

Omitted supported native values follow documented Lima built-in defaults,
not the previous project's settings or the legacy controller defaults. In
particular agent forwarding is now false unless explicitly enabled. Treat native
null values as unset where Lima does; normalize desired values before comparing
state. Containerd-off is the deliberate exception to native defaults. Never
silently inherit unsafe global overrides or prior-project drift.

Host mount locations may be absolute, relative to the config directory, or
`~/...`. Resolve symlinks before validation. Reject host-home/ancestor exposure
and overlapping host/guest mounts. Guest mount destinations remain explicit clean
paths beneath `/work/`. Reject Go-template expressions initially; `{{.Dir}}` is
Lima's instance directory, not our project directory. No Lima `param` support.

## Forwarding variants and selection

### Local forwarding selector (required)

| `portForwarding.backend` | Active local rule source | Inactive rule validation |
| --- | --- | --- |
| `lima` | `lima.portForwards` | Reject populated `localTunnels.forwards` |
| `ssh` | `localTunnels.forwards`; require `localTunnels.backend: ssh` | Reject populated `lima.portForwards` |
| `none` | Neither | Reject either populated local rule list |

Require the selector explicitly, including `none`. No inference from rule
presence, runtime CLI backend override, automatic fallback or silent option
removal. Empty inactive lists and commented-out alternatives are permitted.

Reverse forwarding is independent: omit `reverseTunnels` for no reverse tunnels,
or set `reverseTunnels.backend: ssh` with individual TCP forwards. Explicit
`backend: none` is also allowed only with no populated reverse rule list.
There is no native reverse TCP equivalent.

### Backend capability matrix

| Backend / mode | Individual TCP | Individual UDP | Port ranges | Unix sockets |
| --- | --- | --- | --- | --- |
| Native dynamic, gRPC | Yes | Yes | TCP/UDP, native semantics | Rejected |
| Native static | Yes | Rejected | Rejected in initial version | Rejected |
| Custom SSH local/reverse | Yes | Rejected | Rejected; no expansion | Rejected |

Dynamic native `proto: any` may use TCP and UDP together under Lima's semantics.
Lima 2.3's `FillPortForwardDefaults` defaults omitted/null/empty `proto` to
`any` (TCP and UDP), despite the TCP comment in the default template. Static
native rules must explicitly select `proto: tcp`; do not silently interpret
UDP/any as TCP. With omitted guestIP and `guestIPMustBeZero: true`, Lima defaults
guestIP to `0.0.0.0`; otherwise it defaults to loopback.

Native ranges follow Lima's ordered, equal-cardinality guest/host mapping and
validation, without a custom size cap. Controller-created TCP/UDP listeners must
use 1024–65535; target service ports may be privileged where Lima permits them.
Retain Lima's special SSH-port protections. The controller never requests elevated
privileges to bind a listener.

Explicitly select gRPC for native dynamic TCP/UDP rather than inheriting the
host's `LIMA_SSH_PORT_FORWARDER`. Native static TCP uses Lima's own SSH setup;
custom forwards use our separate SSH connection. Reconciliation must account for
transport on already-running instances, not just set an environment variable on
the next start.

**No Unix socket forwarding**, including socket-to-socket and mixed TCP/socket
mappings, in any backend. The earlier interview agreements about socket support
and socket-specific approval were withdrawn. `ssh.forwardAgent` remains a separate
supported native setting.

### Combinations

| Local variant | Reverse SSH | Valid? |
| --- | --- | --- |
| Native static and/or dynamic | Off or on | Yes |
| Custom SSH local | Off or on | Yes |
| None | On | Yes: reverse-only |
| None | Off | Yes: no project forwarding |
| Native local plus custom SSH local | Either | No in the initial version |

Static and dynamic native rules can coexist only on non-overlapping guest ports:
Lima 2.3's `isPortStaticallyForwarded` suppresses dynamic forwarding by guest port
alone, ignoring protocol and guest IP. Reject these combinations before mutation,
even when the host mappings, protocols or guest IPs are otherwise distinct.
Native and custom local forwarding could technically coexist on distinct ports,
but mixed ownership is deliberately excluded initially. Do not allow duplicate or
conflicting listener mappings. A local and reverse listener sharing a numeric port
are not inherently duplicates: they listen on different machines. Account for
protocol/IP matching when validating native ranges and rule conflicts.

All network listeners remain loopback-only. This is restricted exposure of guest
services, not full network isolation: the default Lima network may still let the
guest reach host services through `host.lima.internal`.

## Configuration examples

These are full alternative files in schema v2, supported by the updated CLI. Choose one rather than concatenating them. Native built-in
defaults are used where fields are omitted.

### A. Native dynamic TCP/UDP/ranges plus static TCP and optional reverse SSH

```yaml
schemaVersion: 2
project: service-a
instance: devbox

environment:
  resolver: ["./scripts/dev-env"]
  timeoutSeconds: 60

portForwarding:
  backend: lima

# Optional: guest localhost:1080 -> host localhost:1080 (our ssh -R).
reverseTunnels:
  backend: ssh
  forwards:
    - listenPort: 1080
      targetHost: 127.0.0.1
      targetPort: 1080

# Alternative custom local forward, NOT enabled in this variant.
# To use it, select backend: ssh and remove the native portForwards below.
# localTunnels:
#   backend: ssh
#   forwards:
#     - listenPort: 8080
#       targetHost: 127.0.0.1
#       targetPort: 3000

lima:
  mounts:
    - location: "."
      mountPoint: /work/service-a
      writable: true
  ssh:
    forwardAgent: true
  mountInotify: false
  containerd:
    system: false
    user: false
  portForwards:
    # Dynamic TCP: host localhost:8080 -> guest localhost:3000.
    - guestPort: 3000
      hostPort: 8080
      proto: tcp
      static: false

    # Dynamic UDP: host localhost:15353 -> guest localhost:5353.
    - guestPort: 5353
      hostPort: 15353
      proto: udp
      static: false

    # Dynamic native range, four corresponding TCP ports.
    # Host 14000..14003 -> guest 4000..4003.
    - guestPortRange: [4000, 4003]
      hostPortRange: [14000, 14003]
      proto: tcp
      static: false

    # Static TCP: host localhost:8443 -> guest localhost:443.
    - guestPort: 443
      hostPort: 8443
      proto: tcp
      static: true
```

Omitted native host/guest IP fields default to loopback under Lima's semantics.
Dynamic forwarding follows guest listener discovery. Static TCP establishes a
fixed forward during startup without requiring the application to be running.
The controller appends its deny-all fallback after the allow rules; it is not
necessary to repeat that policy in every project file. Removing `reverseTunnels`
disables custom reverse forwarding without changing the native local variant.

### B. Custom SSH local and reverse TCP

```yaml
schemaVersion: 2
project: service-a
instance: devbox

environment:
  resolver: ["./scripts/dev-env"]
  timeoutSeconds: 60

portForwarding:
  backend: ssh

# Host localhost:8080 -> guest localhost:3000 (our ssh -L).
localTunnels:
  backend: ssh
  forwards:
    - listenPort: 8080
      targetHost: 127.0.0.1
      targetPort: 3000

# Guest localhost:1080 -> host localhost:1080 (our ssh -R).
reverseTunnels:
  backend: ssh
  forwards:
    - listenPort: 1080
      targetHost: 127.0.0.1
      targetPort: 1080

lima:
  mounts:
    - location: "."
      mountPoint: /work/service-a
      writable: true
  ssh:
    forwardAgent: true
  portForwards: []
```

Custom target hosts may be validated DNS names or IP addresses. No UDP, range,
socket or `static` options are accepted in custom rules. Native containerd is
forced off even though omitted here. Lima receives only the generated ignore
policy, not these custom tunnel targets. Omit reverseTunnels for local-only use.

### C. No local forwarding (optionally reverse-only)

```yaml
schemaVersion: 2
project: service-a
instance: devbox

portForwarding:
  backend: none

# Uncomment for reverse-only operation.
# reverseTunnels:
#   backend: ssh
#   forwards:
#     - listenPort: 1080
#       targetHost: 127.0.0.1
#       targetPort: 1080

lima:
  mounts:
    - location: "."
      mountPoint: /work/service-a
      writable: true
  portForwards: []
```

No resolver means a marker-only project environment, preserving current behavior.
`none` means no project local forwards plus the generated deny-all native policy;
it does not restore Lima's broad automatic forwarding. Lima SSH access remains.
Agent forwarding defaults false here.

## Lifecycle, readiness and failures

- Editing a file does not apply a backend choice. Use `activate`; `provision`
  remains credential refresh only.
- Switching projects retains the existing stop/edit/start isolation behavior.
- Changing native rules or switching local backends requires stop/edit/start.
  Record the backend in host state; identical native policies do not exempt a
  backend transition. Older state without a recorded backend requires activation.
  Custom-only rule changes can avoid a restart when project and native settings
  still match. Detect runtime transport drift as well as YAML drift.
- `plan` never runs the resolver. Show selected backends, native changes,
  generated policy, custom rules, defaults and restart/confirmation reasons.
- Preserve approval before disruptive changes; noninteractive use requires
  `--yes` where approval is needed.
- Readiness means project environment and forwarding setup, not application
  health. Dynamic native rules without a service report 'waiting for guest
  listener' without failing activation. Native static/custom SSH listeners must
  be established, but target applications need not answer.
- Separate configured rules, bound listeners and application health in status.
  Native ownership checks use host `ps` and `lsof` against Lima's host-agent and
  static SSH master PIDs; `lsof` is an added native-status dependency.
  Do not assume that a random process listening on a port proves our forwarding
  owns it. Native UDP requires protocol-appropriate checks, not a TCP dial probe.
- Validation/resolver failures before mutation leave the active project intact.
- After mutation begins, failures mark the project incomplete, clear newly
  installed credentials, close custom tunnels, and stop the VM when needed to
  prevent native forwards remaining exposed. Preserve last known connection
  metadata after readiness failure. If discovery fails or VM status is unknown
  during cleanup, attempt a stop regardless of backend and use shutdown cleanup
  rather than spending the remaining cleanup budget on another SSH attempt.
  Never restore prior credentials automatically. Report cleanup failures rather
  than claiming exposure closed.
- Preserve boot-ID/config readiness, instance locking, private control sockets,
  atomic state writes and secret withholding. Config hashes use normalized
  effective configuration, not comments/formatting or resolved credentials.
- Check effective Lima configuration after global defaults/overrides are merged;
  refuse unexpected mounts/forwards rather than silently accepting wider exposure.

## Implementation sequence

1. Publish the schema, examples and field/default reference. Select a maintained
   YAML parser compatible with the actual Go module (Go 1.26 currently; fix the
   README's older requirement). Keep decoding strict and bounded.
2. Replace TOML input and `init`; implement canonical discovery, YAML-only errors,
   normalization and validation. Reject unknown/duplicate keys, extra YAML
   documents, unsupported tags/templates, invalid paths and incompatible backends.
3. Derive a pure reconciliation plan: native edits, managed tunnels, range rules,
   transport requirements and restart/approval reasons. Preserve unrelated VM
   settings and verify effective post-start configuration.
4. Add a forwarding module seam for the two real adapters. Keep protocol-specific
   native/custom apply, status and cleanup behavior behind it. Native local rules
   are never converted into custom SSH; reverse TCP remains separately managed.
5. Implement native gRPC dynamic forwarding, static TCP verification, custom local
   and reverse TCP, generated deny-all policy, backend switches and fail-closed
   cleanup. Verify native static/dynamic coexistence against Lima 2.3.0.
6. Test CLI/controller behavior: YAML defaults/safety, variant compatibility,
   version checks, native UDP/ranges, invalid static combinations, no socket/SSH
   range support, conflicts, absent applications, global override drift, manual
   restart, resolver failure, rollback, locking and no secret leakage.
7. Run Go tests/race/vet/staticcheck, schema/example validation and repo checks.
   Validate generated complete Lima configs, not the extended project document as
   a standalone Lima template. Update README, QUICKSTART and template comments.
8. Real-VM smoke tests require separate explicit permission. Exercise TCP/UDP/range
   traffic, static/dynamic coexistence, occupied ports, backend/project switches,
   absent services and shutdown/failure cleanup. Automated fake tests alone do not
   establish native forwarding readiness or ownership guarantees.

## Implementation validation

Passed without starting, stopping or editing a real VM:

- `just test`: formatting, race tests (81.8% statement coverage), vet,
  staticcheck and six Python inventory tests.
- Review regressions: native protocol/IP defaults, static/dynamic suppression,
  all six backend transitions, legacy state without a backend, preserved metadata
  after readiness failure, uncertain cleanup/failed stops, and typed readiness.
- `just build`, `just lint` and `just validate`.
- JSON Schema validation of all three example files, this document's full
  examples and a freshly generated `init` file.
- `limactl validate` of temporary complete Lima configurations assembled from
  the base template plus each example's native settings and deny-all policy.
- Real local host TCP/UDP socket ownership parsing with `lsof`; no Lima instance
  was involved in that test.

Native traffic, bootstrap timing, backend switching and cleanup still need
explicitly authorized real-VM smoke tests before claiming end-to-end verification.

## Primary-source research

Read the entire [configuration guide](https://lima-vm.io/docs/config/) through
its [complete printable section](https://lima-vm.io/_print/docs/config/), including
VM types, networks, ports, sudo, mounts, plain mode, environment variables, AI,
GPU, plugins and disks. Inspected versioned source for the behavior that affects
this design. Installed Lima reports 2.3.0; older repo research described 2.2.1.
The live website may describe changes beyond either release.

Findings and owning sources:

- Native attribute types/defaults, host/guest template contexts and global
  config merging: [2.3.0 default YAML](https://github.com/lima-vm/lima/blob/v2.3.0/templates/default.yaml),
  [types](https://github.com/lima-vm/lima/blob/v2.3.0/pkg/limatype/lima_yaml.go),
  [defaults/template evaluation](https://github.com/lima-vm/lima/blob/v2.3.0/pkg/limayaml/defaults.go).
- Native range validation and reverse Unix-socket restrictions:
  [validation](https://github.com/lima-vm/lima/blob/v2.3.0/pkg/limayaml/validate.go).
  Socket capability is a Lima fact, not supported project scope.
- TCP/UDP transport, gRPC versus SSH, dynamic listener discovery:
  [ports](https://lima-vm.io/docs/config/port/),
  [environment variables](https://lima-vm.io/docs/config/environment-variables/).
  Lima's internal transport choice is not our custom backend selector.
- Ordered rules, implicit forwarding fallback and protected SSH ports:
  [host-agent forwarding rules](https://github.com/lima-vm/lima/blob/v2.3.0/pkg/hostagent/port.go).
- Static forwarding uses startup SSH setup and logs setup failures as warnings:
  [host agent](https://github.com/lima-vm/lima/blob/v2.3.0/pkg/hostagent/hostagent.go),
  especially `addStaticPortForwardsFromList` and `separateStaticPortForwards`.
  A successful start is not proof every static forward bound successfully.
  `static` also exists in the [2.2.1 types](https://github.com/lima-vm/lima/blob/v2.2.1/pkg/limatype/lima_yaml.go),
  despite not being described in that default template.
- Running instances cannot be edited:
  [2.3.0 edit command](https://github.com/lima-vm/lima/blob/v2.3.0/cmd/limactl/edit.go).
- Mount restrictions, writable-only inotify and experimental caveats:
  [mounts](https://lima-vm.io/docs/config/mount/).
- Guest access to host loopback through `host.lima.internal` and the VZ-specific
  2.3 hostLoopback control:
  [default network](https://lima-vm.io/docs/config/network/user/).
- Plain mode disables features this controller requires:
  [plain mode](https://lima-vm.io/docs/config/plain/).
- Native `env` persists in configuration/startup and `/etc/environment`, while
  `--preserve-env` affects individual invocations. Neither replaces the existing
  guest session credential contract:
  [default YAML](https://github.com/lima-vm/lima/blob/v2.3.0/templates/default.yaml),
  [environment variables](https://lima-vm.io/docs/config/environment-variables/),
  and the repo's `docs/research/lima-project-environment.md`.
